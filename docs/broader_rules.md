# Broader rule detection with short explanations

This experiment keeps the current improvement active: support unfamiliar words
without making explanations longer. It does not change the tutor UI.

The former filter knew pairs such as speaks→speak but lacked many other words.
The new detector asks the existing local LanguageTool 6.6 service for grammatical
rules, their text positions, and suggested replacements. Its rule engine uses
word forms and sentence context. Our code maps selected **rule IDs** (stable names
for kinds of checks in this pinned version) to short explanations.

For example, “He can repairs the bicycle” is supported by MD_BASEFORM. The detector
requires that a checker replacement reconstruct the model's proposed sentence
exactly. It ignores unrelated spelling/style suggestions and withholds proposals
without one unambiguous supported rule. This is supporting evidence, not proof.
No new Python dependencies, model weights or training are involved.

## Verify and learn

Run from the project directory:

1. `uv run python -m pytest tests/test_grammar_rule_detector.py -q`

   `uv run` uses the project's Python environment; pytest checks behavior
   automatically. Here it verifies exact edits, Unicode offsets, rule restrictions,
   invalid evidence and ambiguous alternatives without starting a server.

   Expected: `12 passed` (timing varies).

2. `uv run python grammar_rule_eval.py development --output /tmp/speakwell-broader-development.json`

   Offline replay reuses saved model/checker outputs to compare a changed filter.
   This command creates a separate report; use an unused output filename.

   Expected: `"cases": 60`, `"offered_on_errors": 20`,
   `"offered_on_correct": 0`, `"error_denominator": 30`.
   Offers are not human-approved useful feedback.

3. Read `evaluation/broader_rules/results.md` for the preserved fresh test results
   and explanations. Fresh checks recognized 13/16 positive examples and withheld
   12/12 negative controls; three failures remain documented.

To reproduce fresh component checks later, start `bash scripts/languagetool.sh`
in a separate terminal. This normally starts the installed local grammar server;
expect startup logs mentioning port 8081 (exact text varies).

Then run `uv run python grammar_rule_eval.py fresh --output /tmp/speakwell-broader-component.json`.
The runner submits original text to local LanguageTool and tests authored
proposals against the frozen detector; it does not call an LLM. Expected:
`"cases": 28`, `"passed": 25`, `"unavailable": 0`, `"llm_calls": 0`.
Do not replace archived reports or call a repeat an independent validation.

Learning checkpoint: explain the difference between a word-pair whitelist and
a rule-ID catalogue. Both have limited coverage, but the latter can apply the
same grammatical rule to words that were absent from our development examples.
Inspect the recorded match ID, span and replacement for “repairs→repair”.

## Limits and next step

The fresh test proposals were authored by the evaluator, not generated by the
model. This isolates detector behavior but cannot establish end-to-end quality.
The same assistant authored the examples and implementation, so these are not
independent expert judgments. All new assignments remain open for human review.

Catalogue coverage and the checker itself can still miss errors. Quotes,
coordination, multiple edits and ambiguous rule matches are withheld. This can
reject useful feedback. Raw checker messages are retained as evidence but not
used as the learner's explanation. No speed claim follows from this experiment.

Keep this improvement active: review the outputs and address the DID_PAST mapping
and missed plurals using grammatical evidence, then use additional fresh cases.
Do not solve the misses by adding the specific test words to the old whitelist.

Sentence-specific explanation refinement: see `grammar_reasons.md` and
`evaluation/broader_rules/reasons_v1/comparison.md`. It changes wording only;
broader detection and its three coverage gaps remain the active work.
